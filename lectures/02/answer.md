### 3. 発展（ファインチューニングが向く場面・向かない場面についての考察）

- **ファインチューニング（SFT / LoRA）が向く場面・向かない場面についての考察**：

  1. **ファインチューニングが「向く」場面（今回の実験で 100% 近い改善が確認できた領域）**：
     - **出力フォーマット・スキーマ・文体の強制（Format & Style Alignment）**：
       - 今回、`format_rate` が `9.5% → 100.0%`（`r=4, ep=10` でも `100.0%`）に達したように、「思考過程や前置きを出さず特定の JSON スキーマ 1 行で返す」「定型の拒否フレーズ（『この FAQ には記載がありません。運営に確認が必要です。』）を厳密な文言で返す」といった**入出力の型・トーン＆マナーの固定**には、少量の SFT / LoRA が極めて高い効果を発揮する。
     - **プロンプト長の圧縮と推論レイテンシ・トークンコストの削減**：
       - Few-shot プロンプティングで毎回 5〜10 例の入出力サンプルをコンテキストに入れる代わりに、LoRA でフォーマットと応答規約を重みに焼き込めば、推論時のシステムプロンプトを最小限に抑えられ、0.8B のような小型モデルでも安定した構造化出力が得られる。

  2. **ファインチューニングが「向かない」場面（今回の失敗事例とセクション 6 が示した限界）**：
     - **事実知識の注入・頻繁に更新される情報の記憶（Knowledge Injection / Dynamic Facts）**：
       - セクション 6 で `「この講座の最終課題の締切はいつですか」` に対して通常課題の締切（9月30日）を `needs_review: false` で断定してしまった通り、数十〜数百件規模の SFT では「モデルが知らない事実知識を正確に教え込む」ことや「訓練データにない事実と訓練データにある事実の境界を厳密に区別させる」ことは困難であり、ハルシネーション（もっともらしい断定）を誘発しやすい。また、提出期限やオフィスアワーのような運用情報が変更されるたびに再学習するのは保守性の面でも不適切である。
     - **偏った少数データでの複雑な論理境界（条件付き保留）の学習**：
       - `「オフィスアワーは事前予約が必要ですか」`（条件1で誤答）のように、既知キーワード（「オフィスアワー」）を含みつつ未知の属性（「事前予約の要否」）を問う質問を正しく棄却するには、Grounded 例だけでなく「同じキーワードを含むが FAQ だけでは答えられない Hard Negative（Ungrounded）例」をバランス良く設計しなければ、エポックを増やした際に多数派クラス（`needs_review: false`）へ過適合する。

  3. **実務システム設計における手法の使い分け（Prompting / Structured Outputs / RAG / SFT の役割分担）**：
     - **第1選択（プロンプトエンジニアリング ＋ Structured Outputs / Constrained Decoding）**：
       - 単純な JSON スキーマの強制であれば、まず API や推論エンジン（vLLM / Outlines / `response_format`）の **Grammar / JSON Schema 制約付きデコーディング** と Few-shot プロンプトで解決すべきであり、これだけで `format_rate = 100%` を学習コストゼロで達成できる。
     - **第2選択（RAG ＋ 明示的な根拠抽出ステップ）**：
       - 今回のような FAQ 応答タスクで「根拠がないときに断定しない（Abstention）」精度を高めるには、いきなり `answer` を出力させるのではなく、検索（RAG）で取得した FAQ チャンクに対し `{"matched_faq_id": ..., "evidence_quote": ..., "answer": ..., "needs_review": ...}` のように**根拠箇所の引用を先に生成させるスキーマ設計（またはプロンプト設計）**が有効である。また、情報が更新される場合はモデルの重みではなく RAG の参照ドキュメント（`FAQ`）側を更新する。
     - **第3選択（SFT / LoRA の適用どころ）**：
       - 上記のプロンプト＋RAG＋制約付きデコーディングを整備したうえで、①「0.8B〜3B クラスの小型ローカルモデルに業務固有の言い回し・定型文・判断基準を蒸留して推論コストを下げたいとき」や、②「Hard Negative（紛らわしい保留例）を十分に収集したデータセットで、ドメイン固有のトリアージ基準（`needs_review` の閾値）を微調整したいとき」に LoRA SFT を組み合わせるのが、AI エンジニアリングとして最も堅牢で費用対効果の高いアプローチである。
