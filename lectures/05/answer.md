### 基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：`app/config.py` の `RAG_TOP_K`（通常のベクトル検索で返す件数）を 5 から 2 に変更した。これだけを変更し、指示文・ツールの説明・取得処理には手を入れていない。索引の再作成は不要だった
- 比較した質問と、固定した条件（モデル・対象資料など）：質問は「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」で固定。モデルは既定の gemini-3.5-flash-lite、対象資料は第1〜3回の本講義（ベクトル検索）、実行は通常モードの `uv run python -m app.agent --trace` で、変更前後とも同じ条件にした。検索だけの確認には `uv run python -m app.retrieval "LoRA 固定 学習 QLoRA 加える"`（エージェントが実際に使った検索語）を使った
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  - ツールの呼ばれ方：変更前後とも `search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'})` を 1 回だけ呼び、モデル応答は 2 回で変わらなかった。件数を変えてもモデル側の振る舞い（検索語の決め方・呼び出し回数）は変わらない
  - 検索で返ったページ（検索のみの実行で確認）：変更前は 5 件（第2回 p.52「LoRA と QLoRA」、p.51「PEFT」、p.60「今日の演習」、p.47「根拠と諸説」、p.61「演習の進め方と提出物（仮）」）。変更後は上位 2 件（p.52、p.51）のみで、答えの根拠になるのはこの 2 ページだった。残り 3 件は用語が似ているだけの弱い関連だった
  - 回答と引用根拠：変更前は「元の重みは固定し、細長い2つの小さな行列（低ランク行列）だけを学習する。QLoRA は元の重みを4bitに圧縮することを加える」と正しく答え、引用は p.51 と p.52。変更後も内容は同じく正しく、引用は p.52 のみになった（固定・学習・4bit圧縮の3点とも p.52 の本文に書かれているため、根拠の不足は起きなかった）
  - 時間・トークン数・費用：変更前は 15.77 秒、入力 3,028 / 出力 166 トークン、推定費用 $0.001323。変更後は 5.89 秒、入力 1,741 / 出力 176 トークン、推定費用 $0.000962。入力トークンは約42%減、費用は約27%減。時間の短縮には API 側の混み具合の違いも含まれているため、件数の効果だけとは言い切れない
- 改善した例と、残る失敗・制約：この質問では、根拠が検索上位の 2 ページにそろっていたため、件数を 5→2 に絞っても回答の正しさは落ちず、弱い関連ページ（演習案内など）がモデルに渡らなくなって入力トークンと費用が減った。一方、答えが複数ページに分散する質問（例：演習 STEP 5 の「複数ページ」タイプ）では、上位 2 件だけでは必要な根拠を取りこぼす危険がある。今回はそのタイプの質問では試していない
- 気づき・疑問：RAG_TOP_K は「多いほど安全」ではなく、質問の根拠が何ページに分散しているかで適正値が変わる設定だと分かった。変更前後でモデルの検索語や呼び出し回数が変わらなかった点も重要で、件数の調整はモデルの振る舞いではなく「渡す材料の量と質」だけを変える。実務では、代表的な質問の種類ごとに根拠ページの分散を測ってから件数を決めるのがよさそうだ

### 実装（前後ページを一緒に返す）

- やったこと：`app/retrieval.py` の `search()` が返す各ページに、同じ資料内の前後1ページの本文を `neighbors` として付けるようにした（`attach_neighbors()` を追加）。ヒット同士で重なるページは neighbors に入れない。`search_materials` の説明文にも、前後のページが付くことを書いた。テストは `uv run pytest -q` で 17 件すべて通過
- 比較した質問と条件：検索だけの実行（`app.retrieval.search`）で、変更前（基礎の記録と今回の変更前実行）と変更後を比べた。モデルへの影響は検索結果の差として見る
- 結果：
  - 必要な根拠を追加できた例：質問「構造化出力 制約付きデコーディング 違い」では、通常検索の上位2件は第3回 p.35「制約付きデコーディング」と p.62「補足：構造化出力の最新動向」で、構造化出力そのものを説明する中心のページ p.34「構造化出力」が入らなかった。変更後は p.35 の neighbors として p.34 が一緒に返るようになり、欠けていた根拠がモデルに届くようになった
  - ノイズが増えた例：質問「LoRA 固定 学習 QLoRA 加える」では、通常検索の p.52・p.51 の2件で根拠が足りていた。変更後は neighbors として p.53「チャットボットの場合：何を FT し、何を FT しないか」と p.50「判断の順番」が加わった。どちらもこの質問への答えにはほぼ関係がなく、渡す本文と入力トークンが増えるだけだった
  - エージェントでの実行（質問「構造化出力と制約付きデコーディングはどう違いますか？」）：変更前は入力 1,516 / 出力 247 トークン、5.2秒で、引用は p.35 のみ。変更後は入力 3,515 / 出力 246 トークン、13.7秒で、構造化出力の定義を p.34、制約付きデコーディングを p.35 と、両方の中心ページを引用して答えられた。入力トークンは約2.3倍になった（時間の差には API の混み具合も含まれる）
- 気づき・疑問：前後ページは「話題が複数ページに分かれている資料」では効くが、1ページ完結の話題ではノイズになる。neighbors にも距離のような関連度の目安が付けられれば、モデルが重み付けしやすくなると思った

### 発展（ベクトル＋前後ページ＋Graph の組み合わせ）

- 設計した取得方法：`app/retrieval.py` に `search_hybrid()` を追加し、ツール `search_materials_hybrid` としてエージェントに登録した。ベクトル検索のヒット（source=vector）を中心に、その前後ページ（source=neighbor）と、Graph 拡張の seeds・expanded（source=graph）を、優先順位 vector > neighbor > graph で重複なく集め、上限12ページまで返す。各ページに「どう見つけたか」を付けるので、モデルが根拠の確からしさを判断できる
- 対象の質問：「第3回の例では、コンパクションとセッションをまたぐメモリはどう違いますか。日々のメモはすべて長期メモリに入りますか」。根拠は第3回 p.13（メモリ／コンパクション）、p.39（実装例：Claude。日々のメモと長期メモリの扱い）、p.40（実装例：OpenClaw）に分散している
- 結果（検索だけの実行、検索語「コンパクション セッションをまたぐメモリ 違い 長期メモリ」）：
  - 基本のRAG（ベクトル検索、上位2件）：p.65「補足：メモリと Context Engineering の最新動向」と p.38「メモリがないと、毎回ゼロからやり直しになる」だけ。日々のメモと長期メモリの区別が書かれた p.39 は入らなかった
  - ハイブリッド：10件返り、p.39 が neighbor として、p.40 が graph として入った。コンパクションの説明は p.65 にも書かれているため、質問の両半分に答える材料がそろった。ただし p.13 自体はどの方式でも拾えなかった
  - ノイズと費用：10件中、p.36「判断モデル」、p.63・p.67「補足」など質問と関係の薄いページも4件ほど混ざった。渡す本文は基本RAGの約5倍で、入力トークンと費用は増える。正確さが要る質問では見合うが、単純な用語質問では基本RAGで十分だと思う
- エージェントでの実行（同じ質問）：ハイブリッドのみを使う構成では、モデル応答2回（検索1回）、入力 6,887 / 出力 473 トークン、7.4秒。基本のRAGでは、モデル応答3回（検索を2回に分けた）、入力 3,435 / 出力 348 トークン、9.0秒。どちらの回答も「コンパクションは同じセッションの中で古い履歴を要約に置き換える仕組み、セッションをまたぐメモリは外の保存先にファイルとして残す仕組み（ともに p.39）」「日々のメモはすべては長期メモリに入らず、毎晩の見直し（dreaming）で基準を超えたものだけが長期メモリに移る（p.40）」と正しく、引用も合っていた
- 比較の結論：基本のRAGでも、モデルが検索を分ければ（指示文でもそう促している）同じ根拠にたどり着けた。ハイブリッドの利点は、検索1回で根拠がそろうので、モデルが検索を分ける判断をしなくても済む点にある。一方で入力トークンは基本のRAGの合計の約2倍で、ノイズページも一緒に渡る。「検索の分け方をモデル任せにしない代わりに、トークンで払う」方式だと分かった
- 気づき・疑問：方式を混ぜると「拾える根拠」は増えるが、上限件数と優先順位の設計がそのままノイズ量を決める。source のタグ付けは、モデルが「graph で拾った候補は弱い根拠」と割り引く手がかりになる点で有効だった
