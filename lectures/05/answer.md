<!-- 基礎・実装・発展のどれか1つに取り組めば完了です。 -->

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：`app/config.py` の `RAG_TOP_K`（通常のベクトル検索で返す件数）を 5 から 2 に変更した。これだけを変更し、指示文・ツールの説明・取得処理には手を入れていない。索引の再作成は不要だった
- 比較した質問と、固定した条件（モデル・対象資料など）：質問は「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」で固定。モデルは既定の gemini-3.5-flash-lite、対象資料は第1〜3回の本講義（ベクトル検索）、実行は通常モードの `uv run python -m app.agent --trace` で、変更前後とも同じ条件にした。検索だけの確認には `uv run python -m app.retrieval "LoRA 固定 学習 QLoRA 加える"`（エージェントが実際に使った検索語）を使った
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  - ツールの呼ばれ方：変更前後とも `search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'})` を 1 回だけ呼び、モデル応答は 2 回で変わらなかった。件数を変えてもモデル側の振る舞い（検索語の決め方・呼び出し回数）は変わらない
  - 検索で返ったページ（検索のみの実行で確認）：変更前は 5 件（第2回 p.52「LoRA と QLoRA」、p.51「PEFT」、p.60「今日の演習」、p.47「根拠と諸説」、p.61「演習の進め方と提出物（仮）」）。変更後は上位 2 件（p.52、p.51）のみで、答えの根拠になるのはこの 2 ページだった。残り 3 件は用語が似ているだけの弱い関連だった
  - 回答と引用根拠：変更前は「元の重みは固定し、細長い2つの小さな行列（低ランク行列）だけを学習する。QLoRA は元の重みを4bitに圧縮することを加える」と正しく答え、引用は p.51 と p.52。変更後も内容は同じく正しく、引用は p.52 のみになった（固定・学習・4bit圧縮の3点とも p.52 の本文に書かれているため、根拠の不足は起きなかった）
  - 時間・トークン数・費用：変更前は 15.77 秒、入力 3,028 / 出力 166 トークン、推定費用 $0.001323。変更後は 5.89 秒、入力 1,741 / 出力 176 トークン、推定費用 $0.000962。入力トークンは約42%減、費用は約27%減。時間の短縮には API 側の混み具合の違いも含まれているため、件数の効果だけとは言い切れない
- 改善した例と、残る失敗・制約：この質問では、根拠が検索上位の 2 ページにそろっていたため、件数を 5→2 に絞っても回答の正しさは落ちず、弱い関連ページ（演習案内など）がモデルに渡らなくなって入力トークンと費用が減った。一方、答えが複数ページに分散する質問（例：演習 STEP 5 の「複数ページ」タイプ）では、上位 2 件だけでは必要な根拠を取りこぼす危険がある。今回はそのタイプの質問では試していない
- 気づき・疑問：RAG_TOP_K は「多いほど安全」ではなく、質問の根拠が何ページに分散しているかで適正値が変わる設定だと分かった。変更前後でモデルの検索語や呼び出し回数が変わらなかった点も重要で、件数の調整はモデルの振る舞いではなく「渡す材料の量と質」だけを変える。実務では、代表的な質問の種類ごとに根拠ページの分散を測ってから件数を決めるのがよさそうだ
