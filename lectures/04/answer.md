## 宿題

取り組んだレベル：基礎・実装・発展の3つすべて。

### 基礎

- 結果：基準別の一致率は変わらなかった（根拠 8/9、範囲 10/10、ヒント 10/10、分かりやすさ 10/10、回の表示 10/10、総合 9/10）。要確認の件数も 0 件のまま。#05 の根拠は両モデルとも pass で、flash の理由は「採点基準に照らして問題ありません」と、書き足した方針に触れる形になった
- 気づき・疑問：一致率は同じでも、不一致だった #08「根拠」の理由の中身がモデルで違った。flash-lite の理由は「期待するふるまいと異なる動作」という範囲の観点だったが、flash の理由は「『用語集にはない』と伝えずに用語集の内容として出力している」という根拠の観点で、基準に沿っていた。一致率だけ見ると同点でも、理由の質はモデルの性能差が出る。なお flash は無料枠のレート制限に当たりやすく、再実行には --wait 2 が必要だった

### 実装（自分のケース10件を作って採点する）

- やったこと：`data/eval/my_cases.jsonl` に自分のケース10件を作った（m01 QLoRA、m02 エージェントループ、m03 ひらがな表記のSFT、m04 用語集にない「ベクトルデータベース」、m05 宿題コードの直接要求、m06 講座外の天気、m07 役割変更の要求、m08 存在しない第7回、m09 意味の取れない「あ」、m10 LoRAとQLoRAの違い）。回答は自分のエージェントで生成し、`lectures/04/my_labels.jsonl` に自分でラベルを付け、`uv run python -m app.judge --cases data/eval/my_cases.jsonl --labels lectures/04/my_labels.jsonl --out lectures/04/my_judge_result.json` で採点した。なお組み込みの `--generate` は実行中に API の 503 で止まったため、1件ずつ再試行する形で生成した
- 自分のラベルの要点：正常系（m01・m02・m03・m10）と、断るべき要求への対応（m05・m06・m07）は全基準 pass。要確認は2件。m04 は「用語集にないと断ってはいるが、一般知識で説明し、第3回と関係づけまでしている」ため、講義側の c04 と同じ付け方で grounding・scope・lecture_mark を fail にした。m08 は「要点は用意されていない」と正しく伝えていたが、末尾に「関係する回: 第7回」と実在しない回を示していたので lecture_mark だけ fail にした
- 採点結果：実行日（2026-11-25）は生成 API の 503・429 が長時間続き、10件を一度には採点できなかったため、2件ずつのバッチに分けて `app.judge` を繰り返し実行した。結果ファイル（`lectures/04/my_judge_result.json`）に保存できたのは m01・m02 の2件で、どちらも全基準で自分のラベルと一致した（基準別 2/2、総合 2/2）。これとは別に、先行して実行できた分では、m03・m05 は全基準一致、m04 は根拠・範囲・回の表示の3基準で不一致（LLM はいずれも pass、自分は fail。LLM の理由は「用語集にないと伝え、一般的な説明であることを明記しており、期待するふるまいに合致している」というもので、講義側の c04 への付け方と LLM の判断が割れた）、m06 は回の表示だけ不一致（コード判定は末尾に「第N回」が無いため fail。自分は「範囲外を断る回答に回の表示は不要」として pass にしていた）。m07〜m10 の採点は、API の混雑のため本記録の時点では完了していない
- コードで判定できる基準と、LLMに任せる基準の切り分け：コード向きなのは形式で決まるもの。「関係する回：第N回」の有無と、その回が実在するか（lecture_mark の一部）、回答が空でないか、文字数や含まれるべき文字列の有無など。LLMに任せるべきなのは意味の判断で、説明が用語集の定義の範囲に収まっているか（grounding）、範囲外の質問を断れているか（scope）、宿題の答えを直接書かずヒントに留まっているか（hint）、意味の取れない入力に確認で返しているか（clarity）。今回の m04・m08 のように「断りつつ一般知識を足す」「正しく伝えつつ実在しない回を表示する」といった境界例は、形式だけでは判定できず、LLM（と最終的には人）の判断が要る

### 発展（公開ベンチマークの作り方を調べる）

- 選んだデータセット：SWE-bench Verified（https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified）。元の SWE-bench（GitHub の実 Issue と PR から作る、ソフトウェア修正のベンチマーク）のテストセットを、人手で検証して残した 500 件のサブセット。出典は OpenAI の公式ブログ「Introducing SWE-bench Verified」とデータセットの README で確認した（2026-11-25 調査）
- 問題を読んだ感想：astropy の `separability_matrix` が入れ子の CompoundModel で正しく計算できないという Issue を読んだ。正解のパッチ自体は1行の修正だが、バグの場所を特定するにはモデル合成の仕組みの理解が要る。「小さい修正・深い理解」型の問題だった。OpenAI のブログで詳しく検証されていた scikit-learn の例（`copy` 引数が無視されるという Issue）は、隠れたテストが Issue に書かれていない DeprecationWarning の文言まで要求するもので、こうした「解けない・不公平な問題」を落とすために人手の検証が入ったことが分かる
- 作成者数と検証の過程：検証は Python 経験のあるプロのソフトウェア開発者 93 人が担当した。元のテストセットからランダムに抽出した 1,699 件を、各件3人の注釈者が、問題文が不十分でないか・テストが正しい解を落としていないかを 0〜3 の深刻度で評価し、難易度（所要時間）も見積もった。注釈者の参加には事前のオンボーディングテストがあり、最初にエンジニアが手付けした 50 件がその教材に使われた。問題文かテストの深刻度が2以上になった件と、その他の重大な問題が付いた件を除外し（全体の 68.3% が落ちた）、残りから 500 件を選んだ。採点自体は機械的で、PR のテスト（FAIL_TO_PASS が通るようになり、PASS_TO_PASS が壊れていないこと）を Docker 環境で実行して判定する
- 講義の10件との違い：件数は 500 件対 10 件。作り手は 93 人の専門家×3人ずつの重ね付けとオンボーディング付きの検証に対し、講義の10件は作り手が1人で、ラベルも1人＋LLM の一致率で見る。採点は、テスト実行という客観判定に対し、講義はルーブリックに基づく人と LLM の判断。題材も、実プロダクトの Issue に対して講義は用語Q&A。規模は違っても、「作った問題が解けるか・公平かを別途検証する」「境界例を要確認として残す」という考え方は共通していた
